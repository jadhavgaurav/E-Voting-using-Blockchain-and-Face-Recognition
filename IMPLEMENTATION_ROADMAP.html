1. Executive Summary

  • Blockchain and AI biometrics are the two P0 pillars; backend, admin/voter workflows, and audit UI are P1; polish and scalability are P2.
  • Source of truth: Model A — on-chain votes are canonical; off-chain DB holds election metadata, candidate mirror, biometric logs, and indexing cache.
  • Voter identity: Email + password for auth; Aadhar mandatory, encrypted in DB and hashed for uniqueness; 1:1 mapping (hashed Aadhar ↔ unique custodial blockchain address) in backend.
  • Voting UX: Backend relayer signs and submits transactions; voters do not manage wallets; Aadhar re-entered at vote time to fetch constituency and active elections.
  • Results: Sealed until election close (commitment-reveal on-chain); tally computed from chain events/state.
  • Legacy: Full rewrite; no reuse of legacy app code. Contract logic and data flows inform redesign only.
  • Testnet: Primary Sepolia; fallback Holesky; local Hardhat network for CI and fast dev.
  • Stack: Next.js (TypeScript strict) + FastAPI (Python 3.12+) + PostgreSQL 16+ + Solidity (Hardhat) + ethers.js in backend relayer.
  • CI: GitHub Actions — typecheck, lint, tests for web, API, contracts; contract tests run on local chain only.
  • Security: No client-side trust for verification or authorization; encrypted Aadhar and embeddings; rate limiting and audit logging throughout.
  • Constituency System: 10 major Indian states with real ECI data; hierarchical selection (State → District → Assembly Constituency); supports Parliamentary, State Assembly, and Local elections; ~344 Lok Sabha + ~2,265 Vidhan Sabha constituencies.

6. Data Flows

Enrollment

Admin creates election and candidates (DB + mirror to chain). Voter registers with email, password, Aadhar, constituency. Backend hashes Aadhar (dedup), encrypts Aadhar, creates custodial wallet, stores mapping; biometric enrollment produces embedding stored in DB (encrypted). Face template linked to voter id.

Verification

Voter logs in (email/password). To vote: enters Aadhar → backend validates, returns constituency and active elections. Then liveness check (blink/head-turn or PAD), then face match against stored template. Backend records VerificationLog (pass/fail, score, PAD result, request_id). Only on pass does backend allow vote-relay step.

Vote cast

Backend checks on-chain that voter's address has not voted for that election. Builds commitment (if sealed) or direct vote, signs with voter's key, submits tx. Stores tx hash in DB as receipt cache; chain is source of truth.

Receipt verification

Frontend shows tx hash and explorer link. Verification: frontend/backend reads tx and VoteCast (or Reveal) event from chain; backend may index events for faster "my receipt" lookup.

Tally/results

After election end, reveal phase (if commitment-reveal) runs; results computed from contract state or events. Admin dashboard and audit export read from chain (or indexed data).

11. Implementation Phases & Sprints

Sprint 0 — Foundations

P0Effort: M

Goal: Repo structure, CI, local dev, type safety, lint/format, constituency data seeding.

Tasks: Monorepo layout (web/, api/, contracts/); Python setup with uv (uv init, pyproject.toml, uv.lock committed); Docker Compose (Postgres, Hardhat local); ESLint/Prettier (web), Ruff/mypy (api); GitHub Actions (uv sync --frozen, typecheck, lint, test); contract tests on Hardhat local; README and .env.example; Seed constituency data: 10 states, ~346 districts, ~2,265 ACs, ~344 PCs from ECI data via Alembic migration.

Acceptance: docker-compose up brings Postgres + chain; uv sync installs all deps; CI green on main; Constituency cascading dropdowns work in registration.

Phase 1 — Blockchain Core

P0Effort: L

Goal: Contract v1 with admin-only candidate registration, one-vote-per-address, election lifecycle, events; deployment scripts; tests.

Tasks: Hardhat project; Election + Candidate + Vote (commit/reveal if sealed); AccessControl or Ownable; uint256 electionId; deployment script; Hardhat tests (local chain); document ABI/address for backend.

Acceptance: Tests pass; deploy to local and optionally Sepolia; backend can read ABI and address from env or artifact.

Phase 2 — AI Biometrics Core

P0Effort: L

Goal: Enrollment and verification services; liveness baseline; face recognition; verification logs; rate limiting.

Tasks: FastAPI routes for enrollment (image → embedding, store encrypted) and verification (liveness then face); InsightFace or ArcFace; liveness (blink/head-turn or lightweight PAD); VerificationLog; rate limiting; unit and integration tests.

Acceptance: Server-authoritative verification; all outcomes logged; no raw images stored by default.

Phase 3 — Integrate End-to-End Vote Cast

P0Effort: L

Goal: Voter flow from login → Aadhar → verification → cast → receipt; backend relayer; receipt verification UI.

Tasks: Backend: voter registration (email, password, Aadhar encrypt/hash, wallet creation), JWT auth, verification orchestration, vote relay (sign + submit tx), receipt storage and endpoints; Frontend: login, Aadhar step, verification steps, cast vote, receipt page with tx hash and explorer link; E2E tests.

Acceptance: One voter can complete flow once per election; receipt verifiable on explorer; duplicate vote rejected by contract and backend.

Phase 4 — Results and Auditability

P1Effort: M

Goal: Results from chain; sealed results (reveal phase if used); audit export; admin dashboards.

Tasks: Backend: results endpoint (read from contract or index); reveal phase automation (if commitment-reveal); audit export (CSV/JSON); Frontend: admin results view, audit export UI.

Acceptance: Results match chain; audit export contains non-sensitive actions and verification summaries.

Phase 5 — Hardening

P1Effort: M

Goal: Rate limiting, abuse testing, concurrency/replay tests, observability.

Tasks: Rate limits on all public and verification endpoints; abuse tests (double vote, replay verification, invalid tokens); concurrent vote simulation; structured logging and request_id; health checks.

Acceptance: Rate limits enforced; no sensitive data in logs; tests document expected behavior under abuse.

Phase 6 — Demo Polish

P2Effort: M

Goal: UX polish, accessibility, optional testnet and cloud deployment guide, optional PAD upgrade.

Tasks: UI copy and loading states; a11y (focus, labels, contrast); docs: testnet deployment (Sepolia, faucet, env vars), optional cloud (Vercel + Railway/AWS); optional: replace baseline liveness with PAD model.

Acceptance: Demo script runs on testnet; docs sufficient for external reviewer.

Key Relationships Summary

  • Constituency Hierarchy: State → District → Assembly Constituency; Parliamentary Constituency spans multiple ACs within same state; AC → Local Bodies
  • Voter Registration: Voter registers with Assembly Constituency as base unit; Parliamentary derived from AC mapping
  • Elections: Election targets specific constituencies via election_constituencies mapping table
  • Candidates: Each candidate belongs to an election_constituency pair (election + constituency)
  • Biometrics: One enrollment template per voter; multiple verification attempts logged
  • Voting: On-chain receipts cached in DB; blockchain is source of truth
  • Audit: All admin/voter actions logged with request_id tracing

  • Voting: GET /voting/my-constituencies (voter's AC, PC, Local), GET /voting/elections (active for voter), GET /voting/elections/:id/candidates, POST /voting/cast
  • Receipts: GET /voting/receipts, GET /voting/receipts/:tx_hash, GET /voting/verify/:tx_hash
  • Results: GET /results/elections/:id, GET /admin/results/export
  • Audit: GET /admin/audit (admin, filters, date range)

13. Frontend Screens

  • Admin: Login; Dashboard (elections list); Create/Edit Election; Manage Candidates; Voter list (pending/accepted/rejected, approve/reject); Results (per election, from chain); Audit export (filters, download).
  • Voter: Login (email/password); Dashboard (active elections); Vote flow: enter Aadhar → constituency + elections → select election → liveness challenge → face capture → submit → "Vote cast" with receipt (tx hash, explorer link).
  • Receipt verification: Input tx hash → show tx status, event (VoteCast/Reveal), election and candidate id; link to block explorer.

14. Blockchain Testnet & Deployment

  • Primary testnet: Sepolia (Ethereum L1; wallets, explorers, faucets; Hardhat/ethers.js support).
  • Fallback: Holesky (same tooling; alternate faucets if Sepolia is down).
  • Mode 1 — Local: Hardhat local network for CI, fast tests, deterministic debugging.
  • Mode 2 — Public testnet: Sepolia (or Holesky) for staging, real explorer links, demo.
  • Deployment: npx hardhat compile; npx hardhat run scripts/deploy --network sepolia. Env: RPC_URL, DEPLOYER_PRIVATE_KEY (never committed), CHAIN_ID, CONTRACT_ADDRESS. Frontend/backend read ABI from artifacts and address from env.
  • Funding: Deployer wallet for contract deployment; voter wallets created per user (backend). Faucets: Sepolia faucet, Alchemy/Infura testnet faucets. Keys only in .env; separate keys for deployer vs voter accounts.
  • Receipt: App shows tx hash, block number, "View on Explorer" link (e.g. sepolia.etherscan.io). Verification: fetch tx receipt and parse VoteCast/VoteRevealed event; backend may cache in on_chain_receipts; chain remains source of truth.
  • CI: All contract tests run on Hardhat local in CI; no CI dependency on Sepolia. ABI and deployment outputs versioned or generated from same codebase.
